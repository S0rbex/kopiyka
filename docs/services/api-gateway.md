# api-gateway

**Одним реченням:** єдині вхідні двері в систему — перевіряють, хто прийшов, і направляють запит до потрібного сервісу.

## Аналогія

Рецепція з охороною в бізнес-центрі. Ти показуєш перепустку, тобі кажуть, на який поверх іти. Офіси всередині не перевіряють кожного відвідувача заново: вони довіряють рецепції. А в технічні приміщення (`/internal/**`) відвідувачів не пускають узагалі.

## Навіщо він потрібен

Без gateway кожен із п'яти публічних сервісів мусив би сам:
- перевіряти API-ключ;
- рахувати ліміти запитів;
- генерувати `Request-Id`.

Тобто той самий код п'ять разів, і п'ять місць, де можна помилитися в безпеці. Крім того, магазину довелося б знати адреси всіх сервісів, а внутрішні API були б доступні з інтернету.

**З gateway в магазину одна адреса**, `http://localhost:8080`. Як влаштована система всередині, магазин не знає й знати не повинен.

## Що він робить

- **Маршрутизація за шляхом:**

  | Шлях | Сервіс |
  |---|---|
  | `/v1/payments/**`, `/v1/refunds/**` | payment-service |
  | `/v1/balance*` | ledger-service |
  | `/v1/events/**`, `/v1/webhook_*` | webhook-service |
  | `/v1/account` | merchant-service |

- **Перевірка API-ключа.** Gateway рахує хеш ключа, питає merchant-service «чий це ключ?» і кешує відповідь у Redis на 60 с.
- **Захист від підробки.** Видаляє всі вхідні заголовки `X-Merchant-*` і додає власний `X-Merchant-Id`. Інакше шахрай міг би надіслати `X-Merchant-Id: чужий_магазин`.
- **Rate limiting:** не більше, напр., 50 запитів/с на магазин. Зайве отримує `429 Too Many Requests`.
- **`Request-Id`** і початок трейсу: за цим ID потім знаходимо весь шлях запиту в Grafana.
- **Фаза 6:** вхід для оператора через Keycloak (JWT), доступ до `/admin/**`.

## Чого він НЕ робить

- Ніякої бізнес-логіки: не знає, що таке платіж.
- **Не повторює `POST`-запити.** Якщо повторити «спиши гроші», можна списати двічі. Повторювати чи ні, вирішує клієнт, використовуючи `Idempotency-Key`.
- Не зберігає ключі. Вони живуть у merchant-service, gateway лише кешує результат перевірки.

## Компроміси, які варто вміти пояснити

- **Відкликаний ключ працює ще до 60 секунд** — поки не протухне кеш. Це свідомий обмін безпеки на швидкість. У фазі 6 merchant-service надсилатиме подію «ключ відкликано», і gateway чиститиме кеш одразу.
- **Якщо Redis упав, лімітер пропускає всі запити (fail-open).** Краще тимчасово без лімітів, ніж увесь API лежить через допоміжний компонент.
- **Ключ хешуємо SHA-256, а не bcrypt.** Ключ — це 32 випадкові байти, його не підібрати перебором. А bcrypt на кожен запит додав би десятки мілісекунд. Для паролів людей — навпаки, тільки bcrypt або argon2.

## Технології

Spring Cloud Gateway (реактивний, на WebFlux) і Redis.
