# Сервіси простими словами

Цей розділ пояснює **суть** застосунку: що він робить, які ролі є в реальному світі платежів і навіщо кожен сервіс. Технічні деталі лежать у `docs/01–06`. Тут — розуміння.

## 1. Що ми взагалі будуємо

Уяви інтернет-магазин чайників. Він хоче приймати оплату карткою, але:
- не хоче сам домовлятися з банком;
- не хоче зберігати номери карток (це дорого й небезпечно);
- не хоче писати логіку повернень і звірок.

Тому магазин підключає **платіжну платформу**. У реальному житті це LiqPay, WayForPay, Fondy, Stripe. **Kopiyka — це наша навчальна версія такої платформи.**

Магазин для нас — **мерчант**, тобто наш клієнт. Покупець, який платить карткою, — клієнт магазину. З покупцем ми напряму не спілкуємося: усе йде через сервер магазину.

## 2. Хто є хто в реальному світі платежів

```
Покупець ──картка──> Сайт магазину ──API──> Kopiyka (ми) ──> Банк-еквайр ──> Visa/Mastercard ──> Банк-емітент
                       (мерчант)          (платформа)                                          (банк покупця,
                                                                                                 напр. Monobank)
```

| Роль | Хто це | Що робить |
|---|---|---|
| Покупець | людина з карткою | платить за чайник |
| Мерчант | інтернет-магазин | продає, інтегрується з нами через API |
| Платформа | **ми, Kopiyka** | приймає платежі для багатьох магазинів, рахує гроші, повідомляє магазин |
| Банк-еквайр | банк, з яким працює платформа | проводить картковий платіж, раз на день переказує нам гроші |
| Банк-емітент | банк, що видав картку | перевіряє, чи є гроші, блокує й списує суму |

Весь правий бік — еквайр, Visa та емітент — у нас замінює **один сервіс `bank-simulator`**. Справжній банк не дасть нам тестовий API, у якому можна вмикати збої на замовлення.

## 3. Історія одного платежу через усі сервіси

Покупець купує чайник за **100,50 грн**. Наша комісія — 2,5 %.

| Крок | Що відбувається | Сервіс |
|---|---|---|
| 1 | Покупець натискає «Оплатити». Сервер магазину каже нам: «створи платіж на 100,50 грн». | `merchant-demo` → `api-gateway` |
| 2 | Gateway перевіряє API-ключ магазину («це справді магазин чайників?») і передає запит далі. | `api-gateway` + `merchant-service` |
| 3 | Створюється запис платежу зі статусом «чекає підтвердження». | `payment-service` |
| 4 | Магазин передає дані картки і просить підтвердити платіж. | `payment-service` |
| 5 | Перевіряємо, чи не шахрай це. | `fraud-service` |
| 6 | Просимо банк заблокувати 100,50 грн на картці, а потім списати їх. | `payment-service` → `bank-simulator` |
| 7 | Платіж успішний, повідомлення про це йде в Kafka. | `payment-service` |
| 8 | Бухгалтерія записує: магазину нараховано 97,99 грн, платформі — комісія 2,51 грн. | `ledger-service` |
| 9 | Магазину надходить повідомлення «оплачено», і він відправляє чайник. | `webhook-service` → `merchant-demo` |
| 10 | Наступного дня беремо звіт банку і звіряємо його з нашими записами. Гроші магазину стають «доступними». | `settlement-service` → `ledger-service` |
| 11 | Покупцеві не сподобався чайник, магазин робить повернення. | `payment-service` + `ledger-service` + `bank-simulator` |

`fx-service` (курси валют) потрібен лише антифроду: щоб порівнювати платежі в доларах з лімітами в гривнях.

## 4. Карта сервісів

| Сервіс | Роль «з життя» | Без нього… | Опис |
|---|---|---|---|
| `api-gateway` | рецепція з охороною | кожен сервіс сам перевіряв би ключі, а внутрішні API стирчали б назовні | [api-gateway.md](api-gateway.md) |
| `merchant-service` | реєстр клієнтів і договорів | не знаємо, хто наші клієнти, які в них тарифи й ключі | [merchant-service.md](merchant-service.md) |
| `payment-service` | менеджер, що веде платіж від початку до кінця | ніхто не керує кроками і не знає стан платежу | [payment-service.md](payment-service.md) |
| `ledger-service` | бухгалтерія | гроші — це просто поле `balance`, яке будь-який баг може зіпсувати | [ledger-service.md](ledger-service.md) |
| `bank-simulator` | зовнішній банк | нема куди «відправляти» платежі й нема на чому тренувати збої | [bank-simulator.md](bank-simulator.md) |
| `webhook-service` | поштар з рекомендованими листами | магазин не дізнається, що оплата пройшла | [webhook-service.md](webhook-service.md) |
| `fraud-service` | служба безпеки | пропускаємо крадені картки | [fraud-service.md](fraud-service.md) |
| `settlement-service` | ревізор і казначей | не помітимо, що наші записи розійшлися з банком | [settlement-service.md](settlement-service.md) |
| `fx-service` *(опційно)* | довідник курсів валют | антифрод не порівняє долари з гривнями | [fx-service.md](fx-service.md) |
| `merchant-demo` | наш перший клієнт (магазин) | API нема на чому перевірити від початку до кінця | [merchant-demo.md](merchant-demo.md) |

## 5. Чому стільки сервісів — чесна відповідь

- **Кожен сервіс відповідає за одну річ і сам володіє своїми даними.** Ledger не знає про картки, payment не знає про баланси, webhook-service не змінює платежі. Межі між сервісами збігаються з межами відповідальності в реальній фінтех-компанії: там окремі команди відповідають за процесинг, бухгалтерію, антифрод і інтеграції.
- **Кожен сервіс навчає окремої теми.** Gateway — безпеці й rate limiting, payment — сагам та ідемпотентності, ledger — транзакціям і блокуванням, webhook — надійній доставці, settlement — batch-обробці, fraud — polyglot і fallback.
- **У реальному стартапі я б почав з модульного моноліту.** Мікросервіси тут — свідомий навчальний вибір. Сказати це на співбесіді — плюс.
- **Мінімальне ядро — 4 сервіси:** gateway, payment, ledger, bank-simulator. З ними гроші вже рухаються. Решта додається по фазах (див. [roadmap](../06-roadmap.md)).

## 6. Три ідеї, на яких тримається весь застосунок

1. **Гроші не можна втратити й не можна списати двічі.** Тому є ідемпотентність, outbox, звірка з банком.
2. **Будь-що може впасти в будь-який момент:** банк, Kafka, наш сервіс посеред запиту. Тому кожен крок записується до виконання, а після збою система з'ясовує, що сталося, а не вгадує.
3. **Кожен сервіс — господар своїх даних.** Чужі дані отримуємо тільки через API або події, а не лізучи в чужу БД.

Порядок читання: спершу цей файл, далі `payment-service` → `bank-simulator` → `ledger-service` → `api-gateway` → `merchant-service`, решта — у будь-якому порядку.
