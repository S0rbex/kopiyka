# merchant-demo (TypeScript)

**Одним реченням:** маленький демо-магазин, який користується нашим API так, як це робив би справжній клієнт.

## Аналогія

Перший клієнт, який погодився протестувати сервіс до запуску. Він не частина платформи. Він — **той, для кого платформу будують**.

## Навіщо він потрібен

- **Перевірити систему від початку до кінця.** Swagger дозволяє викликати окремий ендпоінт, але не прийняти вебхук і не перевірити його підпис. merchant-demo проходить увесь шлях: створив платіж → підтвердив → отримав вебхук → перевірив підпис.
- **Показати, як виглядає інтеграція з боку магазину.** Це прекрасно працює на демо під час співбесіди.
- **Тестувати нашу стійкість.** Він навмисно іноді відповідає на вебхук `500` або «засинає», щоб ми бачили, як працюють ретраї доставки.
- **Контрактні тести (Pact).** merchant-demo фіксує, які саме поля й відповіді нашого API він використовує. CI payment-service перевіряє, що ми їх не зламали. Це consumer-driven contracts між двома різними мовами.

## Що він робить

- Проста сторінка або CLI: «купити чайник за 100,50», вибір тестової картки.
- Викликає наш API через клієнт, **згенерований з `public-api.yaml`** (openapi-typescript).
- Ендпоінт `/webhooks/kopiyka`:
  - перевіряє HMAC-підпис по **сирому** тілу запиту;
  - відкидає надто старі повідомлення;
  - відсіює дублікати за ID події.
- Показує в логах або на сторінці, які події прийшли і в якому порядку.

## Чого він НЕ робить

- Він не частина платформи, тож у проді його не було б. Це клієнт.
- Не зберігає номери карток: передає тестові дані прямо в наш `confirm`.

## Чому TypeScript

Більшість інтернет-магазинів пишуть бекенд на Node.js, PHP, Python тощо — не на Java. Клієнт іншою мовою показує, що наш API справді незалежний від мови, а OpenAPI-контракт працює.

Сервіс маленький, тож вистачить базового знання JS.
